# 写扩散 vs 读扩散

> **TL;DR** — 一份内容要进入 N 个读者的视图：写入时复制到每人（写扩散），还是读取时聚合（读扩散）。默认：受众小、延迟敏感选写扩散；受众大、写入方热点集中选读扩散；大型系统几乎都按受众规模分档混用。

## 是什么 / 解决什么问题

feed、群聊、通知、关注系统共享同一结构：一条内容有 N 个接收者，每个接收者的视图（收件箱 / 时间线）都需要"这份内容"。问题只是**物化视图在写入时构建还是读取时构建**。这一个分岔决定了系统的写放大倍数和读路径延迟，是此类系统最重要的决策。

## 方案谱系

| 方案 | 优点 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| 写扩散（fan-out on write / push） | 读路径极快（收件箱直接拉）；天然离线友好 | 写放大 ×N；存储 ×N；发布延迟随受众增长 | 受众小（几百内）、读多写少、延迟敏感 |
| 读扩散（fan-out on read / pull） | 写路径 O(1)；存储一份 | 读要聚合 N 个来源；缓存难；热门视图反复聚合 | 受众大、浏览频率低、写方热点集中 |
| 混合分档 | 每档各取所长 | 两套代码路径、分档规则要维护 | 受众分布两极分化（社交 feed、群聊） |
| 惰性 / 延迟扩散（lazy fan-out） | 削发布瞬时峰值 | 不在线时读体验退化 | 在线率敏感、允许异步收敛 |

## 取舍要点

- 判断变量就四个：受众规模 N、写频率、每读者读频率、存储成本。**N × 写频率**是写扩散的真实成本；**读频率 × 聚合成本**是读扩散的真实成本
- 群聊是天然分档案例：百人内群写扩散（每人收件箱一份，延迟最好）；万人群必须读扩散（每条消息 ×10000 次写会打死存储）。分档阈值要可配置
- feed 的对称案例：普通用户写扩散、大 V 读扩散，否则单条动态触发百万次写
- 写扩散的隐性收益：每份副本可独立定制（已读状态、删除、过滤），读扩散做不到
- 读扩散的热点保护：热门源（大 V、活跃群）必须加缓存层，否则 O(N) 聚合每次都打到存储
- 副本一致性：写扩散各副本短暂不一致是常态，要有收敛机制（读时校验或异步对账）

## 常见误区

- 只算写成本不算读成本（读扩散在热视图上的聚合成本同样惊人）
- 写扩散不设受众上限（写放大随受众无界增长）
- 混合方案缺清晰分档规则 → 两边劣势叠加
- 给长期离线 / 僵尸账号也实时扩散（白写，不如上线时惰性补）
