# 实时下行通道

> **TL;DR** — 服务端要在亚秒级把事件（新消息、通知、协作状态）送到客户端时的通道选型。默认：在线客户端用 WebSocket 长连接，App 退后台 / 被杀用厂商推送（APNs/FCM）唤醒，长轮询只做低频或兼容兜底。

## 是什么 / 解决什么问题

HTTP 是"客户端发起请求—服务端响应"的模型，服务端没有原生的主动推送能力。要把事件主动送到客户端，必须在 HTTP 之外维持一条反向通道。选通道 = 在四个维度上做权衡：**延迟、并发连接的运维成本、实现复杂度、到达可控性**。

## 方案谱系

| 方案 | 优点 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| 短轮询 | 实现最简单，服务端无状态 | 延迟 = 轮询间隔；大量空查询 | 分钟级敏感度、小规模 |
| 长轮询 | 延迟可到亚秒；HTTP 兼容性完美 | 每条消息一次完整 HTTP 往返；服务端 hold 大量挂起请求；断开重连风暴 | 低频事件、兼容兜底 |
| SSE | 单向推流实现简单，自带重连语义 | 只能下行（上行另开 HTTP）；部分代理 / 移动端环境支持差 | 纯下行、浏览器为主 |
| WebSocket | 全双工；帧开销小；有连接态与心跳 | 连接生命周期要自管（心跳、重连、退避）；网关有状态；移动端耗电 | 双向实时、高频事件 |
| 厂商推送（APNs / FCM / 国内厂商通道） | 复用系统级长连接；App 被杀也能到达 | 延迟与到达率不可控（秒级、可丢弃）；payload 小 | 移动端后台唤醒、角标 |

## 取舍要点

- 有双向交互（聊天、协作）选 WebSocket；纯下行通知 SSE 更省事；事件频率低到分钟级，长轮询就够
- 移动端的现实：前台靠长连接保活，后台被系统冻结后只有厂商推送可达。厂商推送只承担"唤醒/提示"，**不承诺业务数据送达**——数据永远走自家"上线拉取"兜底
- 百万级长连接的成本不在选型而在运维：连接状态外置（user→gateway 路由表），网关才能无状态化、随时重启；重连必须随机退避，防止服务恢复瞬间的重连洪峰二次打挂
- 长连接上只跑下行推送和少量轻量信令；业务请求（发消息、拉历史）走普通 HTTP API——在异步通道上做请求/响应关联的复杂度不值得

## 常见误区

- 把 APNs/FCM 当业务主投递通道（到达率不承诺，会丢）
- 长轮询的挂起请求不设超时与并发上限 → 连接堆积打爆服务
- 重连不随机抖动 → 故障恢复瞬间重连风暴
- 心跳间隔照搬 PC 时代经验：移动网络中间设备（NAT）超时更短，心跳必须匹配运营商链路
