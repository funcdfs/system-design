# 投递语义

> **TL;DR** — 系统对"一条消息会到达几次"的承诺：at-most-once 可能丢，at-least-once 可能重复，exactly-once 极贵。默认：不允许丢的业务选 at-least-once，重复交给接收侧幂等去重收敛；承诺 exactly-once 前先算清跨服务两阶段的成本。

## 是什么 / 解决什么问题

网络会丢包、进程会重启，所以重试是必须的；而"重试"与"绝不重复"天然冲突。投递语义就是系统在这个冲突上的明确承诺，它决定三件事：**ack 的时机、重试的边界、接收端要不要去重**。

## 方案谱系

| 语义 | 实现手段 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| at-most-once | 发完即忘（fire-and-forget），不重试 | 最快；可能丢消息 | 允许丢：指标上报、非关键通知 |
| at-least-once | ack + 超时重试（有限次数 + 退避），重试复用同一消息标识 | 可能重复，接收端需幂等 | 不允许丢的绝大多数业务 |
| exactly-once | at-least-once + 接收侧按唯一键去重；或跨服务事务 / 去重表 | 写路径多一次往返或两阶段提交，吞吐显著下降 | 重复不可接受：计费、转账 |

## 取舍要点

- 先问哪个代价更致命：丢失 vs 重复。重复几乎总能用幂等键兜住，丢失兜不住——所以 **at-least-once + 幂等是默认答案**
- "exactly-once"的承诺边界：MQ 的 exactly-once 只到 MQ 边界为止；端到端恰好一次 = at-least-once + 消费幂等 + 端侧去重，没有免费的午餐
- ack 的语义要对齐业务含义：服务端"已落库"不等于对端"已看到"。对用户有意义的 ack 是端到端回执
- 离线投递是 at-least-once 的自然延伸：推不动就存着（收件箱模型），上线拉取。推送重试次数有限，最终兜底永远是"拉"
- 重试必须有退避和上限，否则故障期的重试流量会放大原故障

## 常见误区

- "用了 Kafka / 事务，所以是 exactly-once"——语义只覆盖到该组件边界，跨边界要重新证明
- 服务端落库就给发送方回"已送达"（接收方可能根本没收到）
- 重试无退避、无上限 → 重试风暴
- 离线消息"只保留最近 N 条"而不与接收端已确认位点对齐 → 上线漏消息
