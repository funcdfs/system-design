# 宽列存储

> **TL;DR** — 行键分区 + 动态列族的 NoSQL 家族（Cassandra / HBase / Bigtable 模型）。默认：高吞吐写 + 按主键读的负载（聊天记录、时序数据、feed 原始数据）选它，同时接受放弃跨行事务与强二级索引。

## 是什么 / 解决什么问题

为"写吞吐与水平扩展优先"的负载设计的存储模型：数据按 partition key 分布到集群各节点，同一行键下可挂任意多列（动态列 / 列族），写入走 LSM-Tree（内存表顺序刷成不可变 SSTable）。它用关系模型的能力（join、跨行事务、丰富二级索引）换取写入吞吐和弹性扩展。

## 方案谱系

| 方案 | 优点 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| Cassandra / ScyllaDB | 哈希分区线性扩展；无主多副本；一致性可调；CQL 生态；原生 TTL | 二级索引弱（常用查询表自维护）；无跨行事务；读放大要设计 | 高吞吐写 + 主键点查/范围扫，多数据中心 |
| HBase / Bigtable 模型 | 范围分区利于扫描；单行强一致；生态成熟 | 依赖重（HDFS / ZooKeeper）；运维复杂 | 大范围扫描、有序遍历 |
| DynamoDB | 全托管、容量弹性 | 按请求计费成本模型；热点分区限流要设计 | 云上托管优先、不想运维存储 |
| （对照组）MySQL 分库分表 | 事务、索引、生态 | 写吞吐天花板低；分片与扩容运维痛苦 | 数据量未到分水岭、团队关系型能力更强 |
| （对照组）KV（Redis 等） | 延迟最低 | 内存容量经济性差；持久化语义弱 | 热路径缓存，不做 PB 级主存储 |

## 取舍要点

- 负载画像匹配才选：写多读少、append-only、按分区键点查或键范围扫、无 join——聊天记录是教科书场景（按会话分区，聚簇键按 seq 排序）
- **分区键设计决定一切**：目标是负载均匀 + 单分区大小有界 + 查询都走分区键。热分区（拿时间当唯一分区键、超级大群）要用复合键或分桶打散
- LSM 的账：写吞吐高是用读放大换的（memtable + SSTable 合并读），靠 bloom filter 和键分布局部性兜底
- 一致性级别是旋钮不是信仰：ONE（默认，快而弱）到 ALL（慢而强）按查询重要性逐条选；全调 ALL 等于放弃它的可用性优势
- TTL 与保留策略：原生过期是聊天场景的关键能力（自动删除策略不用自建清理任务），过期由 compaction 兜底回收
- 二级查询需求靠"查询表"解决（写入时多写一张反查表），等价于自己维护索引

## 常见误区

- 分区键选低基数字段或纯时间字段 → 热分区打挂单节点
- 单分区无界增长（万年群聊）→ 要按时间 / seq 分桶
- 把 CQL 当 SQL 用（join、聚合、跨分区事务不存在）
- 一致性全调 ALL 换"强一致" → 写可用性归零，选它的理由消失
- 无界大行（一行挂百万列）→ 列数要和读取模式匹配
