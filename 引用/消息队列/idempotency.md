# 幂等与去重

> **TL;DR** — 同一操作执行多次的效果与执行一次相同（f(f(x)) = f(x)）。默认：操作携带"产生方生成的"唯一键（client_msg_id / 请求 id），接收与存储侧按键去重，把 at-least-once 收敛成"效果上恰好一次"。

## 是什么 / 解决什么问题

重试（网络超时、切换、重连）必然产生重复投递与重复请求。幂等是让重复无害的机制：没有它，任何 at-least-once 系统都会把重复直接暴露成重复扣款、重复消息、重复日志。

## 方案谱系

| 方案 | 优点 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| 天然幂等操作（绝对值覆盖 set） | 零成本 | 不适用于增量操作 | 能用"最终值"描述的操作 |
| 唯一键约束（DB unique key） | 数据库兜底，最可靠 | 依赖单一存储；插重报错要处理 | 落库型操作 |
| 去重表（处理前检查"已处理"键） | 通用 | 写路径多一次读写；表要定期清理 | 关键操作、频率可控 |
| 内存去重（LRU / 布隆过滤器） | 快，无额外 IO | 重启即失效；布隆有误杀需二次确认 | 高频链路、允许概率性初筛 |
| 状态机 / 版本号（CAS） | 顺便解决并发与乱序 | 只适合有状态的对象 | 状态迁移类操作 |

## 取舍要点

- 幂等键必须在**操作的发起方**生成，并随重试复用——服务端生成的 id 在重试时会变成新 id，等于没有幂等
- 去重放在哪：成本敏感的高频链路放端侧 / 内存（LRU 窗口 ≈ 迟到消息的最大时延）；关键链路放存储（唯一键）。两层可叠加：内存初筛 + 存储兜底
- 去重窗口要覆盖"重试可能晚到的最长时间"，窗口太短 = 迟到的重复穿透
- 幂等常与顺序一起出现：去重键 + 单调序号组合（先按键去重、再按序收敛），比单靠任何一种都便宜

## 常见误区

- 用数据库自增主键当幂等键（重试就是新主键）
- 只去重服务端推送，不去重端侧拉取（推和拉都会重复）
- 把布隆过滤器当唯一防线（有误杀，必须配二次确认）
- 幂等键的 TTL 早于业务重试上限 → 键过期后重复穿透
