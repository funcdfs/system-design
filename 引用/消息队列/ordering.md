# 消息顺序

> **TL;DR** — 全局严格有序在分布式系统里极贵（单一序列化点锁死吞吐），且多数业务并不需要。默认：按业务单元（会话 / 分区键）承诺有序，用单元内单调序列号实现，跨单元不承诺；接收端把跳号当常态处理。

## 是什么 / 解决什么问题

顺序有三层，混在一起讨论没有结果：**发送序**（业务上谁先发生）、**存储序**（写进了哪个分区）、**呈现序**（用户看到什么）。用户实际只在乎呈现序稳定。而任何"全局有序"都需要一个序列化点（单分区、全局锁、全序广播），吞吐被它锁死——所以真正的问题是：**有序的承诺范围切到多小，业务仍然成立**。

## 方案谱系

| 方案 | 优点 | 代价 | 适用条件 |
| ---- | ---- | ---- | -------- |
| 全局有序（单分区 / 全序广播） | 序最干净 | 单点吞吐上限；热点集中 | 总吞吐 < 单点能力，且业务真需要全序 |
| 分区有序（按 key 路由，分区内 FIFO） | 水平扩展；实现成熟（MQ 分区、DB 分片） | 只保分区内有序，跨分区无承诺 | 有天然业务分键：会话 id、账户 id、对象 id |
| 单元内单调序列号（发号器 / 存储分配 seq） | 端侧可检测空洞并补齐；多端可比对位点 | seq 分配点的协调成本；要处理发号后写失败 | 会话、文档、账户等有"消费单元"的场景 |
| 逻辑时钟（Lamport / 向量时钟） | 只依赖因果，无需全局协调 | 只保因果序不保全序；向量时钟存储 O(n) | 并发冲突检测，不适合呈现序 |
| 物理时间戳排序 | 实现零成本 | 跨机器时钟不可比（NTP 漂移） | 非正式的显示辅助，不能当唯一依据 |

## 取舍要点

- 先定有序的"单元"：IM = 会话，Feed = 作者或时间线，支付 = 账户。按单元分区，问题从"全局"塌缩为"单元内"——这是绝大多数场景的答案
- seq 由谁分配：写存储时分配（序与持久化绑定、最稳，协调成本高）vs 独立发号器（如 Redis INCR，快，但要接受发号成功 / 写失败的跳号）。**跳号必须允许**：接收端按"最大连续 seq"推进位点即可
- 空洞是常态不是错误：重试、失败、分区切换都会跳号。接收端推进"连续前缀"，发现空洞回源拉取补齐
- 多端同步靠 per-device 位点：每端记录各自已确认的连续位点，换端上线从位点续传——顺序保证与同步保证共用同一个 seq 体系
- 乱序容忍度本质是产品问题：若 200ms 内的乱序能自愈且用户无感，就不值得为"零乱序"支付全局序列化的代价

## 常见误区

- 说"MQ 保序"却不带分区键——乱序不是 MQ 的锅，是路由键的锅
- 用到达时间 / 物理时间戳当呈现序（多发送方并发时 UI 顺序抖动）
- 为全局有序把流量塞进单分区（吞吐灾难，还美其名曰"保序"）
- 向量时钟用在呈现序上（复杂度翻倍，给出的承诺反而更弱）
